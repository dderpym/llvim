# `core/log.py`: Log, Snapshot, Message, Request, Author

A `Log` is a view of one log: a sequence of messages kept as a git branch. Anyone can read it and watch it change. To change it, claim a [Writer](writer.md). The log hands out one Writer at a time, by priority and then by arrival. `Log` is the only code that touches git; the Writer goes through it.

```python
log = Log("/home/me/code/myproject")        # the log "main" of the project
async with log.claim(Request(priority=0, data="me"), timeout=5) as writer:
    writer.append(b"hello")
    await writer.commit()
async for snapshot in log.changes():        # now, then after every change
    show(snapshot.messages, snapshot.uncommitted, snapshot.removed)
```

- `Log(project, name="main", *, repo=None, bucket=500)`:
  - `project` is the project's folder. A relative path is taken from the working folder.
  - `repo` is where the project's git repo is kept. By default it is in the store, under the project's flattened path.
  - `bucket` is how many messages share one folder in a commit (see below).
  - A bad log name, or the root folder as the project, raises `ValueError`. The log need not exist; an unwritten log is empty.
- `head()`: the latest commit, or `None` for an empty log.
- `read(at)`, a `Snapshot` of `head`, `messages`, `uncommitted` and `removed`:
  - no `at`: the head plus the holder's uncommitted writes. `uncommitted` is the messages that are new or differ from the head. `removed` is the head's messages that the writes removed, as the head has them;
  - a commit: exactly what it holds, with nothing uncommitted. An unknown commit raises `ValueError`.
- `changes()`, async: an iterator of snapshots, the first at once, then one each time the log may have changed.
- `claim(request, timeout=None)`, async: the Writer, once it is your turn. `async with` releases it on leaving.
  - Not your turn within `timeout` seconds: raises `TimeoutError`, and you leave the queue.
  - `timeout=0`: the log only if it is yours at once.
  - Cancelled: you leave the queue.
- `holder()`: the request of whoever holds the log, or `None`.
- `queue()`: the holder's request first, then the waiters', in the order they will get the log.
- `Author(name, email="")`: who a commit says wrote it ([writer.md](writer.md)). A name that is empty, or a name or email that git cannot record (`<`, `>`, a line break), raises `ValueError`. `LLVIM` is the default author, and every commit's committer.
- `fork(name, at)`, async: a new log starting at `at` (default: the head). Raises `FileExistsError` if `name` already has commits, `ValueError` if there is nothing to start from, and `RuntimeError` with git's message if git would not make the branch for another reason.

## Using it

- The store is `$LLVIM_STORE`, else `~/.llvim/sessions`. A project is one bare git repo, and a log is the branch `refs/heads/<name>` in it. A new session is a new name: its log starts empty.
- The repo of `/home/stoler/Documents/a` is `home-stoler-Documents-a` in the store. In each part of the path, `%` becomes `%25` and `-` becomes `%2D` before the parts are joined with `-`.
- `changes()` may give a snapshot that equals the last one: something changed that a snapshot does not show, such as a new waiter. Ask `holder()` or `queue()` then.
- Close a `changes()` iterator you stop early (`contextlib.aclosing`, or `aclose()`), or it keeps its inotify instance until it is garbage collected. Each running `changes()` and `claim` holds one, and the kernel limits how many a user may have (`fs.inotify.max_user_instances`). Both use inotify, so they work only on Linux.
- `claim`, `changes`, `fork` and `Writer.commit` need a running event loop; the rest are plain calls.
- While the log is held, each running `claim` and `changes()` keeps one thread blocked on the holder's lock. It is a daemon thread, so a program can exit while the holder lives on, and it ends when the holder lets go.
- A commit that finds more than `PACKS` (50) packs, or about `LOOSE` (6,700) loose objects, starts `git repack -d --geometric=2` in a background thread. The commit does not wait for it, and only one repack runs at a time.
- `Request.data` must be JSON-serializable: other processes read it.
- Each `Log` keeps a cache, and runs one `git cat-file` process from its first read until it is garbage collected. A streaming read costs a directory listing and the journal bytes written since the last read. The first read after a commit fetches only the buckets that commit changed. It then rebuilds the message list, which is linear in the log's length (about 12 ms at 20,000 messages). `read(at)` of an old commit replaces the cache, so the next read of the head fetches again what differs.
- Tasks and threads may share a `Log`. Each `changes()` has its own watch, so two of them never take each other's wake-ups.

## Why it is this way

- **Async where it waits on something outside the process.** Claiming waits on other claimants, watching waits on file events, and committing and forking wait on git. Those are async, so a program can race them against its own input: a viewer waits on the keyboard and the log in one `asyncio.wait`, and a provider can stream a reply while it watches for someone who outranks it. Reading, the Writer's edits and `release` work from memory and local files in well under a millisecond, so they stay plain calls. A sync API that also handed out the inotify file descriptor was rejected: it put inotify outside core.
- **Changes come as snapshots, not as wake-ups.** `changes()` makes its watch before its first read. So a change made between two snapshots always brings another one. With a separate `wait()`, every caller had to read, then wait, and rely on events having queued in between. Changes that pile up while the consumer is busy come as one snapshot, which is what a screen wants.
- **A timeout is a claim's own.** Only `claim` can take its ticket back out of the queue. A caller that gave up on its own, by checking `holder()` first or by abandoning a waiting thread, either raced another claimant or left its ticket queued: it kept outranking others, made the holder's `outranked()` true, and finally took the log for nothing. Timing out or cancelling runs the same cleanup as any error in `claim`.
- **`uncommitted` and `removed` compare with the head; they do not list the writes.** A reader wants to know how the log differs from its last commit, not how the holder got there. So an append that is removed again shows as nothing, a replace with the same content shows as nothing, and a restore shows as the messages it changes and removes. A removed message keeps the content the head has, so a viewer can still show what is going.
- **One git repo per project, one branch per log.** Forking is then making a ref, and every commit of every log can be read with `read(at)`. History is kept the git way, with nothing of our own to keep consistent with it.
- **The store holds a project under its whole path, flattened.** Every repo is one folder directly in the store, so `ls` shows every project. Nested folders that mirror the path were rejected: they are deep to browse, and one project's repo can sit inside another's folders. Escaping `-` and `%` keeps the name unique: `/a-b/c` is `a%2Db-c` and `/a/b-c` is `a-b%2Dc`. Otherwise both would be `a-b-c`.
- **A commit holds `messages/<bucket>/<id>` and `next`.** One blob per message, so a commit stores only the messages that changed. Messages are grouped in buckets of `bucket` ids, named by their first id (`messages/500/512`). Git rewrites every tree on the path of a changed file, so with one flat folder a commit would rewrite a tree with an entry for every message, and writing would get slower as the log grew. With buckets it rewrites one bucket and the short list of buckets.
- **The bucket size can change.** A message stays in the bucket it was first written to. Only new messages use the current size, and reading never computes a bucket, it lists them. So logs written with different sizes, or with several sizes, read and write correctly.
- **`next` is the next free id.** It is kept so that an id is never reused, even after its message is removed. Ids are not taken from the message count, because a remove would then give the same id to two messages.
- **Reads are cached, because readers read on every change.** A viewer reads on every streamed chunk. Without a cache that is three git processes and every message, every time: 58 ms at 5,000 messages. The cache keeps the last commit read, bucket by bucket. A bucket whose git tree did not change is reused without asking git, and inside a changed bucket a message whose blob did not change is reused. It also keeps the live view: the journal's offset, the messages with the journal applied, and the ids the journal touched, so a read applies only the new records and compares only touched ids with the head. A read that finds nothing new returns the same snapshot object. The head is read from the ref file, not from a git process. The cache is best effort: whenever the head, the holder or the journal file differs, the view is rebuilt from the commit.
- **A commit moves the head only if nothing else moved it.** `Writer.commit` raises `Moved` then. The commit is built on a scratch ref. The branch moves in one `update-ref` transaction that checks the branch still points at the commit the writes started from. Holding the claim does not stop raw git, or another program, from moving the branch. Overwriting would silently drop its commit. When `update-ref` fails, the head is read again: `Moved` only if it really is somewhere else, and otherwise git's own error. Taking every failure for a race would send a writer to release and claim again over a stale `main.lock`, which a new claim does not remove, so every commit after it would fail the same way. `fork` does the same: `FileExistsError` only if the branch is there. `fast-import` was not allowed to move the branch itself: it only refuses moves that are not fast-forward, so it would accept a branch moved backwards.
- **Git runs with llvim's settings only.** Every git process gets an environment with none of the user's `GIT_` variables, no global or system config, and `GIT_SETTINGS` passed in by `GIT_CONFIG_COUNT`. A repo is made with no templates. Without this, a `core.hooksPath` or `init.templateDir` in the user's config would run their hooks on every commit: `update-ref` runs `reference-transaction`, and a failing hook fails the commit. A `GIT_DIR` left by a hook llvim was started from would point every command at another repo, and `GIT_NAMESPACE` would hide the log's branches. The settings travel in the environment, not in the repo's config file, so repos made before a setting existed get it too.
- **The committer is always llvim; the author is the caller's.** In git the committer is who made the commit and the author is who wrote what is in it, and that is the split here: the program that writes the log says who it writes for (a model, a user), and llvim made the commit. The message is the caller's too, since only it knows what the content means.
- **The repo is tidied as it grows.** fast-import leaves a pack for every commit, or loose objects for a small one, and nothing ever merges them. After a few thousand commits, every object lookup would search thousands of packs or files, and file handles would pile up. So a commit that finds too many starts a repack. `--geometric=2` merges small packs into larger ones and takes in the loose objects. Each object is rewritten a few times over the log's life, where `-a` would rewrite the whole repo every time. The thresholds are git's own `gc.autoPackLimit` and `gc.auto`, estimated the way `git gc --auto` does it. Running `git gc --auto` itself was rejected: it is a process on every commit, and its full repack rewrites everything.
- **One `fast-import` per commit.** It takes every changed message inline in one process. `hash-object`, `mktree` and `commit-tree` would take one process per changed message and two more for the trees.
- **A running `git cat-file --batch` instead of a process per read.** Reading a commit means reading its tree, the bucket list, the changed buckets and the changed blobs, one after the other. As separate processes that is several milliseconds; through one long-running process it is a pipe round trip each.
- **Claims are files with a lock in them.** Each claimant puts a file `ticket.<arrival>.<random>` in the log's folder and holds an `flock` on it while it lives. The holder renames its ticket to `held.…`. The kernel releases the lock when the process dies, however it dies. So a dead holder or waiter is noticed by anyone who tries the lock, without timeouts or heartbeats. A file whose lock can be taken is dead, and the next claim deletes it. A pid file was rejected: pids get reused.
- **A ticket is complete before it shows up.** It is written and locked as `new.…`, then renamed into place. A reader never sees a ticket with no request in it, and never sees one that is unlocked but alive.
- **One short mutex decides who is next.** Claiming takes the mutex, deletes the dead claims, and takes the log only if there is no live holder and this ticket is first. Without it, two claimants who saw different queues could both take the log.
- **The queue is ordered by priority, then arrival.** Arrival is a counter one higher than any ticket in the folder, so it needs no clock. The holder is never preempted: `Writer.outranked` tells it someone higher is waiting, and yielding is its choice.
- **A priority is one int.** Every claimant's priority is compared with every other's, so they must all be of one comparable type. An int is enough: a ranking of several criteria can be folded into one number. It is held by the type only, not checked at runtime.
- **Uncommitted writes are in a journal on disk.** That is how a reader in another process sees a reply as it streams. The journal starts with the commit it was written on top of. A reader applies it only if that commit is still the head. Otherwise the holder has just committed (and the head already holds the writes) or someone moved the head. Either way the head alone is right. The journal is read before the head, so a reader that loses this race sees a newer state, never an older one.
- **The journal of a dead holder is ignored, then deleted.** A reader only reads the journal of a `held.…` file whose lock is held.
- **Waiting is on kernel file events, never polling.** Every change makes an event in the log's folder: a ticket or journal written, renamed or deleted. A process that dies closes its ticket, which it had open for writing, and that close is an event too. So a holder's death wakes its waiters. That close event is not enough on its own, though. The kernel sends it before it lets go of the dying process's locks, so a waiter woken by it can still find the holder alive, and no event follows. So `claim` and `changes()` also keep a thread blocked on a shared lock of the holder's file. The kernel wakes the thread exactly when the lock goes, however the holder died. Each of them notes the holder before its first read, so a holder that dies between a read and the next wait is noticed as a change. Readers open files read-only and do not write, so reading never wakes anyone, and two waiters cannot wake each other forever. `claim` ignores journal events, so a streaming holder does not wake every waiter on every chunk. The inotify descriptor goes to the event loop with `add_reader`. Portable stdlib watching does not exist, and polling would cost either latency or CPU. So llvim uses inotify through `ctypes`, which is Linux only. kqueue support was left out until it can be tested.
